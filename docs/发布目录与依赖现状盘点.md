# 发布目录与依赖现状盘点

> 检查基线：`feature/atlas-wpf-native-ui` 当前 PR39 分支；仅做静态盘点，不代表已经完成发布包实测分类。

## 结论

当前项目适合朝「主程序 EXE + 少量必要 DLL + 功能/资源文件夹」演进。暂时没有必要把所有现有功能拆成插件，也不应该把开发源码放进玩家发布目录。

## 已确认的项目事实

- 主项目：`SpirePatch.csproj`
- 技术栈：`.NET 9 / WPF`，目标框架 `net9.0-windows`
- 主程序集名称：`SpirePatch`
- 当前正式发布脚本使用 `win-x64`、`--self-contained true`、`PublishSingleFile=false`
- 当前显式 NuGet 包引用：`SharpCompress 0.50.7`
- 项目把 `catalog-plan.json`、`patch-catalog.json`、`InstallerBridge.ps1`、`SelectionBridge.ps1`、`ManagerUpdateWorker.ps1` 嵌入主程序集。
- 发布脚本随后整理文档、第三方许可证并生成 `manager-files.json`。
- 源码文件（`.cs`）属于仓库/构建输入，不应出现在玩家发布目录。

## 现有发布文件的初步分类

| 类别 | 当前来源/例子 | 建议方向 |
|---|---|---|
| 启动入口 | `SpirePatch.exe` | 保留在根目录 |
| 主程序集 | `SpirePatch.dll` | 单文件主程序实验中可合并；若采用普通发布则由发布布局收纳，不要让玩家手动处理 |
| .NET/WPF 运行时 | `System.*`、`Microsoft.*`、`WindowsBase.dll` 等 | 属于自包含运行时依赖；是否合并由单文件发布验证决定 |
| 第三方托管依赖 | `SharpCompress.dll` 及其传递依赖 | 先核对单文件兼容性和许可证，再决定合并或收纳 |
| 原生运行库 | 发布输出中的原生 DLL（如有） | 先识别用途；不能仅凭扩展名一律合并 |
| 程序清单/配置 | `manager-files.json`、运行配置 JSON | 保留为更新器可读取的独立文件，除非验证证明可安全内嵌 |
| 产品资源 | 图标、图片、主题、模板等 | 归入 `Resources/` 或嵌入资源 |
| 用户数据 | MOD 记录、补丁记录、设置、缓存 | 与程序安装目录隔离；不得被程序升级覆盖或清理 |
| 文档与许可证 | `使用说明/`、`third_party/` | 保留为文件夹，不混入运行依赖 |

## 当前缺少的证据

本次静态检查还不能逐个断言每个发布 DLL 是否可删除、可合并或必须独立保留。需要从一次干净的 Windows x64 发布输出生成机器可读清单，至少记录：

1. 相对路径、文件大小、SHA-256。
2. PE 文件类型（托管程序集/原生 DLL/EXE）。
3. 托管程序集的 AssemblyName、版本及是否为第三方依赖。
4. 文件是否被主程序、更新器或启动流程直接引用。
5. 单文件发布后该文件是内嵌、外置，还是运行时提取。

## 推荐的目标玩家目录

```text
尖塔修补站/
├── SpirePatch.exe
├── 必要运行库.dll                 # 仅保留确有必要的少量原生/外置依赖
├── Plugins/                       # 未来可选功能；当前不强制迁移现有功能
├── Resources/                     # 外置资源（确有需要时）
├── 使用说明/
├── third_party/
└── 数据/                          # 仅便携模式；默认用户数据应独立于程序目录
```

## 下一步（小步实施）

1. 在 Windows CI 中对普通发布输出生成依赖清单，不改变现有 ZIP。
2. 对照单文件实验输出，标出哪些文件已合并、哪些仍外置、哪些因原生依赖必须保留。
3. 确认更新器能识别并安全更新这些外置文件。
4. 再决定是否调整默认发布布局。

## 暂不做的事情

- 不迁移现有 MOD 管理、补丁管理、更新中心等成熟功能到插件。
- 不引入复杂的插件依赖解析或第三方插件 SDK。
- 不删除任何现有 DLL 或运行配置。
- 不改变当前正式发布方式，直到依赖清单和升级/回滚验证完成。
