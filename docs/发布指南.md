# 管理器版本自动发布指南

本指南对应仓库当前的 `.github/workflows/release.yml`。正常发布不再手动打包 ZIP、不再手动创建 Draft Release、不再手动上传附件，也不再手动生成或提交客户端更新索引。

管理器更新分为两个相互隔离的通道：

- 稳定版：客户端读取仓库根目录 `manager-update.json`。
- Beta：客户端读取仓库根目录 `manager-beta-update.json`。

这两个 JSON 是客户端固定 Raw URL，必须一直留在仓库根目录。发布工作流只更新当前发布所属的索引文件。

## 1. 发布前准备

### 更新项目版本

编辑 `SpirePatch.csproj`：

- `<Version>` 使用三段基础版本，例如 `0.14.4`。
- `<InformationalVersion>` 同样填写基础版本，例如 `0.14.4`。
- 两者必须完全相同，不能把 `-beta.1` 写进项目文件。
- `<IncludeSourceRevisionInInformationalVersion>false</IncludeSourceRevisionInInformationalVersion>` 保持关闭，避免额外提交后缀影响客户端识别。

Beta 的完整标识由发布工作流在编译时注入程序集的 `InformationalVersion`。例如发布标签 `v0.14.4-beta.1`，程序程序集的 `InformationalVersion` 会是 `0.14.4-beta.1`，而程序集基础版本仍是 `0.14.4`。这能让客户端正确识别当前安装的是 Beta，而不会把 Beta 当成稳定版。

### 编写本版发布说明

在 `releases/` 下新增与标签完全一致的说明文件：

- 稳定版：`releases/v0.14.4.md`
- Beta：`releases/v0.14.4-beta.1.md`

文件必须存在且内容非空。说明应写清变更、验证范围、已知限制和更新注意事项。GitHub Release 正文由工作流直接读取该文件。

提交代码、项目版本和发布说明后，再选择下列任一种触发方式。

## 2. 触发方式 A：推送版本标签

这是常规发布方式。

1. 确认待发布提交包含正确的 `SpirePatch.csproj` 版本和 `releases/v<tag>.md`。
2. 在该提交上创建标签。
3. 将标签推送到 GitHub。

正式版示例：

```powershell
git tag v0.14.4
git push origin v0.14.4
```

Beta 示例：

```powershell
git tag v0.14.4-beta.1
git push origin v0.14.4-beta.1
```

标签以 `v` 开头并匹配 `v*` 后，GitHub Actions 自动启动。工作流以标签指向的提交为发布目标。

## 3. 触发方式 B：GitHub Actions 手动触发

不想本地创建标签时，可以在 GitHub 页面执行：

1. 打开仓库的 **Actions**。
2. 选择 **Publish release**。
3. 点击 **Run workflow**。
4. 选择要发布的分支或 ref。
5. 填写版本号，例如 `0.14.4` 或 `v0.14.4-beta.1`。
6. 如果发布 Beta，勾选 Beta 开关，并使用 `-beta.N` 后缀。
7. 点击运行。

手动输入的版本号可以带或不带开头的 `v`。如果版本号带 `-beta.N`，工作流会强制按 Beta 处理；勾选 Beta 却没有 Beta 后缀会被拒绝。

手动触发使用所选 ref 对应的提交作为目标。工作流会自动创建 Release 标签，不需要再手工创建 Draft Release。

## 4. GitHub Actions 自动执行什么

两种触发方式进入同一套工作流：

1. **版本校验**：校验标签/输入版本、通道、发布说明、`SpirePatch.csproj` 的 `Version` 和 `InformationalVersion`。
2. **Windows 构建与隔离检查**：安装 .NET 9 SDK，执行 `scripts/打包.ps1 -BuildOnly`，并运行现有构建、隔离测试和 WPF 回归。
3. **Beta 程序版本标识**：稳定版使用基础版本作为程序集 `InformationalVersion`；Beta 编译时注入完整的 `x.y.z-beta.N`。
4. **组装发布目录**：复制玩家使用说明、两份发布指南、本版更新内容、鸣谢、第三方声明和许可证。
5. **声明与许可证完整性检查**：确认来源标注、第三方声明和 `third_party/` 两份许可证存在、非空且与仓库源文件 SHA-256 一致。
6. **生成程序清单与 ZIP**：先生成文件清单，再创建 `SpirePatch-v<tag>-win-x64.zip`；同时再次检查 ZIP 内的声明和许可证。
7. **创建 GitHub Release**：正式版创建普通 Release 并设为 latest；Beta 创建 Pre-release，并设置 `latest=false`。
8. **上传与摘要核验**：上传程序 ZIP 和 `校验信息.json`，确认 GitHub 附件 digest 与本地 SHA-256 一致。
9. **更新对应客户端索引**：Release 创建且附件校验通过后，工作流切换到最新 `main`，只更新本次发布所属的 JSON，并通过 fetch/rebase/retry 安全提交。

整个过程中不需要手动创建草稿、上传附件或提交更新索引。

## 5. 稳定版与 Beta 的严格区别

| 项目 | 稳定版 | Beta |
|---|---|---|
| 标签格式 | `v0.14.4` | `v0.14.4-beta.1` |
| GitHub Release | 普通 Release | Pre-release |
| GitHub latest | 设为最新正式版 | `latest=false` |
| 程序程序集 `InformationalVersion` | `0.14.4` | `0.14.4-beta.1` |
| 客户端更新索引 | 只更新 `manager-update.json` | 只更新 `manager-beta-update.json` |
| 稳定版用户 | 可检查到稳定版 | 不会被 Beta 更新覆盖 |

**通道隔离是硬性规则：**

- 稳定版发布只能生成并提交 `manager-update.json`。
- Beta 发布只能生成并提交 `manager-beta-update.json`。
- Beta 流程绝不能暂存、覆盖或提交 `manager-update.json`。
- 两个 JSON 的现有内容不会由本次文档整理 PR 改写；只有未来成功发布对应通道时，Actions 才会更新相应文件。

## 6. 版本号规范

当前客户端的版本解析只支持正式三段版本和 `-beta.N`：

- 正式版：`v主版本.次版本.修订版本`，例如 `v0.14.4`。
- Beta：`v主版本.次版本.修订版本-beta.序号`，例如 `v0.14.4-beta.1`、`v0.14.4-beta.2`。
- 三段数字不能有不必要的前导零。
- Beta 序号从 1 开始，不允许 `beta.0`、`beta.01` 或超长序号。
- 不使用 `-rc.1`、`-preview` 等其他预发布后缀；当前客户端不会按 Beta 版本正确解析它们。
- 同一个已发布标签不可复用或覆盖。需要修复时，发布更高的新版本。

`SpirePatch.csproj` 中的 `Version` 和 `InformationalVersion` 都填写基础三段版本。发布工作流会校验二者相同；Beta 完整后缀只在构建时注入程序集，不改项目文件中的基础版本。

## 7. 本地检查与测试边界

日常开发可在 Windows + .NET 9 环境执行：

```powershell
pwsh ./scripts/打包.ps1 -BuildOnly
pwsh ./scripts/测试发布流程.ps1
```

- `-BuildOnly` 执行构建和仓库配置的隔离检查，不会生成正式发布 ZIP。
- `测试发布流程.ps1` 使用隔离临时目录和模拟 GitHub Release 数据，验证稳定版/Beta 索引写入隔离、JSON 字段兼容性，以及鸣谢与许可证检查。
- 完整安装、回滚和真实游戏环境验证需要独立的隔离样本；GitHub Build/Release Actions 通过不代表真实多人联机或完整对局已验证。

## 8. 发布包必须保留的来源与许可证

每个玩家发布包必须包含：

```text
鸣谢与来源.md
THIRD-PARTY-NOTICES.md
third_party/
  WorkshopAndroidDownloader-LICENSE.txt
  SharpCompress-LICENSE.txt
```

打包脚本会检查这些文件存在、非空，并核对包内内容与仓库源文件一致。不要移动这两份声明文件或 `third_party/` 许可证，也不要从发布包中删除“尖塔补给站”的来源标注。

## 9. 发布失败时

- 版本、发布说明或 `InformationalVersion` 校验失败：先修正项目版本或发布说明，再重新触发。
- Build/隔离检查失败：查看对应 Actions job 日志，不要跳过检查强行发布。
- 附件 digest 不一致：工作流会停止索引更新；先确认 Release 附件和校验信息。
- 更新索引提交冲突：工作流会基于最新 `main` 重试，不会 force-push。
- Beta 发布后客户端仍看不到更新：确认选择了「测试版 Beta」，并检查 `manager-beta-update.json` 对应的 Release 标签和附件摘要。

不要手动复制 Beta 内容到稳定版索引，也不要为了绕过检查而修改客户端固定 Raw URL。
